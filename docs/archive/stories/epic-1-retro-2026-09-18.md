## Findings

### Spec-to-implementation reconciliation

- **[Process, story 1.1]** Le bloc gelé (frozen-after-approval) de `spec-1-1-initialiser-le-dépôt-et-protéger-main.md:29-30` prescrivait d'automatiser la protection de branche via l'API REST classique de GitHub authentifiée par Personal Access Token et `curl`. Cette automatisation a été interrompue en cours d'exécution à la demande explicite de l'humain, jugée trop complexe/coûteuse pour ce réglage ponctuel, et remplacée par une configuration manuelle via l'interface web GitHub (`spec-1-1...md:93`, Implementation Notes). Dans le même esprit, la revue automatisée à 3 sous-agents (step-04) a été volontairement sautée pour cette story, l'humain ayant signalé un coût en tokens déjà trop élevé pour un diff de 29 lignes (`.gitignore`) (`spec-1-1...md:96`). **Disposition :** accepté comme déviation — la correction a déjà eu lieu en session, à l'initiative de l'humain ; rien à corriger rétroactivement. **Leçon amont :** pour un réglage plateforme ponctuel sans outil dédié dans l'outillage installé (ex. pas de tool MCP GitHub pour la protection de branche), la spec devrait par défaut prescrire l'UI web plutôt que planifier de l'automatisation API/curl+token — c'est déjà la pratique recommandée pour ce projet (cf. mémoire de session sur les trous d'outillage plugin) mais elle n'était pas encore reflétée dans le gabarit de spec au moment de la Story 1.1.
- **[Process, comparaison 1.1 vs 1.2-1.5]** La story 1.1 est la seule à porter une section « Review Findings » + « Rejected » longue (6 items retenus, 9 items rejetés, dont 4 rejets qui répètent la même cause racine — « le correctif éditerait la spec gelée elle-même » — pour 4 constats distincts au lieu d'un seul). Les stories 1.2 à 1.5 utilisent un format « Review Triage Log » plus compact (4, 0, 0, 10 items, mais classés `low`/`medium`/`high` avec disposition claire, sans la même redondance). **Disposition :** accepté comme déviation isolée à 1.1, pas un défaut récurrent de l'épic — le process s'est visiblement resserré tout seul dès 1.2. **Leçon amont :** quand plusieurs findings rejetés partagent la même cause racine « non corrigible ici, bloc gelé », les regrouper en un seul constat plutôt que d'en écrire un par occurrence évite de gonfler artificiellement le nombre de findings sur une story déjà signalée comme à faible risque.
- **Critères de réussite déclarés de l'épic** (`epic-1-context.md:19` : « `melos run analyze` et `melos run test` passent sur les squelettes vides, et un push direct sur `main` reste refusé ») — satisfaits d'après les preuves consignées dans les stories (1.5 Implementation Notes : les 4 scripts melos revérifiés après coup, tous passent ; 1.1 Implementation Notes : commit de test `348c9c2` refusé par GitHub après configuration). Non ré-exécuté indépendamment dans cette session de rétro (voir preuves manquantes ci-dessus) — **disposition : accepté sur preuve documentée, pas re-vérifié**.
- **Story 1.4 a déjà corrigé, dans le même épic, le seul vrai défaut inter-stories détecté** : les scripts `melos.scripts.test`/`gen` définis en Story 1.2 ne passaient jamais par `melos exec`, donc ne s'exécutaient jamais réellement sur les packages membres (`apps/mobile`, `apps/admin`) — trouvé et corrigé pendant la revue de 1.4, avant même cette rétrospective (`spec-1-4...md:35`). C'est exactement le type de défaut de frontière entre stories que cette rétro est censée détecter — ici il l'a été par le processus normal, sans attendre la rétro. Aucun angle mort résiduel identifié dans la correction (les 4 scripts sont revérifiés en exécution réelle par 1.5).
