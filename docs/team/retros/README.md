# Rétrospectives d'organisation

Après chaque follow-up (voir `docs/PROCESS.md`) : ce qui marche, ce qui ne marche pas, ce qu'on change. Le jury veut voir une organisation qui apprend, pas une organisation figée. Dix lignes suffisent.

## Format

Un fichier par rétro, `docs/team/retros/AAAA-MM-JJ.md` :

```markdown
# Rétro — AAAA-MM-JJ

## Ce qui marche

- …

## Ce qui ne marche pas

- …

## Ce qu'on change

- … → ticket #<n> (`organisation`)
```

## Règles

- Chaque changement décidé devient un ticket étiqueté `organisation` (un ticket = un changement, pas un fourre-tout), et s'il change la façon de travailler, une entrée dans `docs/DECISIONS.md`.
- Pas de nom de personne dans le fichier de rétro : un fait, jamais un reproche individuel.
- La rétro se lit en réunion, elle ne s'y rédige pas à zéro : un brouillon en continu vaut mieux qu'une page blanche le jour J.
